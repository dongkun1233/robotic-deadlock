# 예전에는 BO·PSO가 좋아 보였는데 지금은 그렇지 않은 이유

이 문서는 실제 코드 감사와 통제 재실행을 구분한다. 교차로 수만 바꾼 통제 실험은 아직 하지 않았으므로 '교차로가 6개여서 BO가 나빠졌다'는 인과 결론은 내리지 않는다. 과거 발표 표의 모든 수치를 재현했다는 주장도 하지 않는다. 과거 사용자 제공 결과 중 출처와 실행 조건이 불확실한 값은 증거로 삼지 않는다.

## 1. 가장 직접적으로 확인한 원인: 기존 비교의 진입 자격 차이

기준 소스: `0375300c72dd7e6fd90022ea557a6cf099a1211b`, `rware/fcfs_cross_simulation.py`.

- `_admit_next_fcfs`: 큐 첫 차량이 `_compatible_with_shared_area`를 만족하지 않으면 바로 반환한다.
- `_admit_next_by_score`: 현재 대기 차량에서 compatible 후보들을 먼저 필터링한 뒤 점수를 비교한다.

따라서 이전 FCFS 대 가중치 정책에는 '진입 가능한 다른 차량을 보낼 수 있는가'라는 제어 규칙 차이가 포함된다. 이는 BO 대 PSO의 상대 순위까지 설명하지는 않는다. 그 둘은 같은 가중치 정책의 최적화 방식이기 때문이다.

이 영향을 따로 측정하기 위해 기존 400개 single_cross 학습 시나리오를 그대로 재실행했다. 새 `FeasibleFCFS` 진단 클래스는 통과 가능한 첫 후보를 큐 앞으로 옮긴 뒤 기존 FCFS 메서드를 호출한다. 이동, 경로, 차량 수, 출발 계획, 호환성 판정, 용량 2, 수집 윈도 2단계는 그대로다. 가중치는 사용하지 않는다. 실행 전 두 인스턴스의 차량별 경로·메타데이터가 같은지 확인했다.

| 기존 시나리오 유형 | 기존 엄격 FCFS | 통과 가능한 후보 중 FCFS | 변화 |
|---|---:|---:|---:|
| 1 | 61.87 | 53.63 | -8.24 |
| 2 | 62.19 | 53.57 | -8.62 |
| 3 | 74.62 | 67.23 | -7.39 |
| 4 | 63.17 | 58.44 | -4.73 |
| 전체 400개 | 65.4625 | 58.2175 | -7.2450 (-11.07%) |

총 800회 모두 완료했다. 400쌍 중 빨라진 경우 395, 동일 3, 느려진 경우 2였다. 가능 후보를 앞세운 횟수는 3,023회다. 이 결과는 교차로를 늘리지 않고도 큰 변화가 생긴다는 증거다. 과거 보고된 FCFS 65.46과도 재실행 값이 일치한다. 다만 특정 BO 가중치와의 원래 비교를 전부 재실행한 것은 아니므로, 과거 성능 차이 중 정확히 몇 %가 규칙 때문이라고 일반화하지 않는다. 395회의 개선도 독립적인 정책 최적성 증명이 아니다.

현행 6교차로에서 두 정책 모두 동일하게 후보를 필터링하면, FCFS는 학습 87.0375 → 84.1750, 검증 88.7000 → 84.7000이다. 이 새 FCFS는 예전 엄격 FCFS보다 강한 기준선이다.

## 2. Basic과 학습 출발점의 의미도 달랐다

과거 코드에는 여러 비교 파이프라인이 공존한다. 아래 사실을 모든 과거 실험에 일괄 적용하지 않는다.

- `scripts/run_total_time_bo_policy_comparison.py`의 Basic/fixed search는 수동 가중치, 한 변수 변화, 병목 프로필 및 일부 무작위 후보를 합친 미리 구성한 집합을 평가한다. 순수 무작위 탐색과 같지 않다. 이 스크립트에서 BO는 그 Basic 최적점을 `initial_weights`로 받고 같은 cycle 시나리오를 더 탐색한다. 해당 cycle 성능 표만으로 별도 테스트 일반화 성능을 평가할 수는 없다.
- `final_output/cycle_weight_search_100_aggressive/README.md`도 Fixed 50개 탐색 후 그 최적점에서 BO 50회를 추가했다고 적고, 같은 100개 cycle에서 Fixed 49.95, BO 49.66을 보고한다. 이 기록은 독립 재검증 전에는 역사적 파일 내용으로만 취급한다.
- `scripts/run_transfer_generalization_train.py`에서는 Basic의 5분/30분 상위 가중치를 BO·PSO에 전달한다. 이 과정은 Basic 검색과 BO·PSO를 결합한 warm-start 파이프라인이다. 각 최적화기의 개별 시간만 동일하다고 해도 선행 Basic 탐색 비용과 그 정보를 받는 효과는 별도로 회계 처리해야 한다. 반드시 부적절한 실험이라는 뜻은 아니지만, 독립적으로 동일한 출발점에서 비교한 실험과는 질문이 다르다.
- 현행 multicross 비교는 각 시드에서 세 방법에 같은 여섯 무작위 초기 가중치, 같은 24회 목적함수 평가를 준다. 현재 `basic`은 실제 무작위 탐색이다.

또한 `scripts/analyze_layout_policy_results_and_select_bo.py`에는 BO가 다른 방법보다 가장 유리한 사례를 고르는 `_select_best_bo_case`가 존재한다. 이런 사례를 시각화하는 것은 설명용으로 가능하지만, 이를 전체 성능 근거로 쓰면 선택 편향이 생긴다. 발표에 그 사례가 실제 사용되었는지는 이 코드만으로 확정할 수 없다.

## 3. 교차로 수와 함께 바뀐 문제 분포

기존 400개는 균형·출발 집중·방향 편중·출구 집중 등의 유형을 나눠 구성했다. 새 학습 80개는 차량 24/48대 × 출발 윈도 20/0의 네 조건이고, 출발·도착 게이트를 난수로 정한다. 다음 차이가 동시에 존재한다.

- 한두 구역 대 여섯 구역, 경로가 여러 구역을 통과하는 연결성.
- 기존 single_cross 9개 CP 구조 대 새 반복 교차로의 2×2 core 및 전체 local path+첫 출구 셀 예약.
- 같은 구역의 마지막 목적지 경쟁 대 현재 로컬 출구 셀 경쟁 등 변수 의미의 차이.
- 교통 수요 유형, 학습 시나리오 수 400 대 80, 검증 자료와 최적화 예산의 차이.
- 기존 후보 수집 윈도와 현행 즉시 결정의 차이.

연결 구역에서는 출구 이후의 정체가 다음 결정에 전파된다. 현재 exit/path 변수는 대기 후보끼리의 관계이고 실제 다음 통로 점유율을 측정하지 않는다. 이것은 관측 정보가 부족할 수 있다는 구조적 가설이다. 교차로 수만의 원인으로 단정하거나, 하류 혼잡도 추가가 반드시 개선한다고 말할 수 없다.

## 4. 새 규칙에서는 가중치가 개입할 기회 자체가 제한된다

학습 80개와 v2에서 선정한 BO 세 가중치를 고정하고 두 규칙을 비교했다. 경로 digest를 확인한 640회 진단 실행이며 최종 테스트는 사용하지 않았다.

FCFS의 진입 시도 기록 중:

| 지표 | strict_first | feasible_first |
|---|---:|---:|
| 대기 후보가 2대 이상인 시도 | 9,563 | 7,868 |
| 실제 진입 가능한 후보가 2대 이상인 시도 | 3,067 | 1,950 |
| 막힌 1순위 때문에 가능한 대안을 보내지 못한 시도 | 1,849 | 0 |
| 가능한 후보끼리 exit 값이 다른 시도 | 712 | 258 |
| 가능한 후보끼리 path 값이 다른 시도 | 1,026 | 376 |

새 규칙의 대기 후보 경쟁 시도 7,868회 중 실제로 2대 이상을 비교할 수 있었던 것은 1,950회(24.8%)였다. 가능한 후보가 한 대이면 점수와 무관하게 그 차량을 고른다. exit/path가 가능한 후보 사이에서 구별되는 비율은 각각 258/1,950=13.2%, 376/1,950=19.3%였다. 두 후보만 계산한 대칭 개수는 같아지지만, 전체 대기 후보 중 필터를 거친 부분집합이라면 원래 값이 달라질 수 있다는 점도 구분한다.

주의: 반복 시도가 들어간 기술 통계다. 정책마다 경로 진행과 큐 궤적도 달라지므로 위 빈도 차이를 곧바로 각 변수의 인과 효과나 독립 표본 수로 해석하지 않는다.

## 5. BO·PSO의 탐색이 충분했는지도 아직 불확실하다

현재 PSO는 입자 6개와 총 평가 24회이므로 초기 평가 뒤 전체 입자 갱신은 3회다. v2 시드 303에서는 평가 4의 초기 후보가 마지막까지 최선이었다. 시드 202는 초기 84.6875에서 84.5875로 0.1단계만 개선했고, 그 가중치의 검증 평균은 88.225였다. BO 시드 202는 마지막 24번째 평가에서도 최저값을 갱신했다. 이 결과로 충분한 수렴을 주장할 수 없다.

목적함수도 가중치가 유도하는 이산적인 순위 선택으로 정해져 매끄럽지 않을 수 있다. 현재 BO는 고정 RBF 커널과 후보 풀을 쓰는 작은 구현이다. 현재 PSO 설정이나 이 BO 구현의 한정된 예산 결과를 모든 PSO/BO의 성질로 일반화하지 않는다. 이론상 더 큰 예산·다른 초기 시드에서 순위는 바뀔 수 있지만, 개선과 검증 일반화가 보장되지는 않는다.

또 하나의 진단: `waiting=1`, 나머지 0인 점수 정책은 현행 학습 80개에서 새 FCFS와 차량별 전체 결과가 정확히 같았다. 즉 현행 정책군은 이 기준선을 표현할 수 있다. 그러나 현재 초기 여섯 무작위 후보에는 그 정확한 기준선이 반드시 들어 있지 않다. BO 시드 202와 PSO 시드 202는 탐색 후에도 학습 FCFS보다 나빴다. 이는 정책군에 FCFS가 없는 문제가 아니라 제한된 탐색에서 그 근방을 놓칠 수 있음을 보여준다. 다음 예산 비교에서는 모든 방법에 같은 FCFS 가중치를 공통 anchor로 포함하는 별도 프로토콜을 고려할 수 있다. 이번 ablation 중간에 초기값을 바꾸지는 않았다.

저장된 검증 결과에서 BO·PSO를 무작위 탐색과 직접 짝지어 비교해도, v1의 BO-무작위 차이 -0.4167단계의 95% 구간은 [-1.0333, +0.2417]로 0을 포함했다. v2의 BO-무작위는 +0.6667 [ +0.2417, +1.1167 ], PSO-무작위는 +1.2500 [ +0.4750, +1.9750 ]였다. 양수는 더 느리다는 뜻이다. 이 세 학습 시드에 조건부인 시나리오 bootstrap에서는 무작위 쪽이 유리하게 나타났지만, 개발 자료의 반복 사용·다중 비교 미보정·학습 시드 3개라는 한계가 있어 최적화기 전체의 우열로 일반화하지 않는다. FCFS 대비 구간이 0을 포함한다는 사실과 BO 대 무작위 구간이 0을 포함하지 않는 것은 서로 다른 비교이므로 모순이 아니다.

같은 seed·예산·코드를 그대로 재실행하면 결정론적 결과는 같다. 새 규칙에서의 full 재탐색은 이미 완료되었으며, 새로운 시도는 예산·시드 등을 사전에 정해 추가해야 한다.

## 6. 지금 진행한 실험과 다음 해석

새 feasible_first 규칙을 고정하고, 네 변수 각각을 제거한 모델을 무작위·BO·PSO 각각 24평가 × 3시드 × 학습 80개로 재최적화한다. 총 추가 목적함수 평가는 864회(69,120개 시뮬레이션)다. full은 같은 조건으로 이미 실행한 216평가를 그대로 사용한다. 검증도 full의 기존 400행을 재사용하고 제거 모델의 1,440행을 추가한다. 각 제거 모델의 해당 가중치는 모든 후보에서 정확히 0이다.

최적화기 사이에는 같은 초기 후보를 사용하지만, full 4차원과 제거 모델 3차원의 초기 후보는 같지 않다. 따라서 결과는 유한 탐색 예산에서의 추가 효용이며 전역 최적해 간 비교가 아니다. 변수 하나를 빼도 나머지가 보상할 수 있다. 차이가 작다고 그 변수가 모든 상황에서 무의미하다는 뜻은 아니다.

검증 세트는 이미 여러 번 본 개발 자료다. 최종 독립 테스트 80개는 닫아 둔다. 성능이 좋은 시드만 골라 결론을 바꾸지 않고 세 시드와 모든 방법의 결과를 함께 보존한다.

## 7. 이번 ablation의 실제 결과

추가 학습 864평가/69,120회와 새 검증 1,440회가 모두 완료됐다. 학습 및 검증 미완료 0, 검증 중복 0이다. 기존 full/FCFS 검증 400행을 합친 파일은 1,840행이다. 아래는 동일 검증 40개 × 학습 시드 3개의 평균 완료 단계이며 낮을수록 좋다. FCFS 기준은 84.70이다.

| 모델 | 무작위 탐색 | BO | PSO |
|---|---:|---:|---:|
| full | 84.4917 | 85.1583 | 85.7417 |
| without_waiting | 87.0417 | 87.0000 | 87.1000 |
| without_maneuver | 84.6083 | 84.6333 | 84.7000 |
| without_exit_competition | 85.2500 | 84.4667 | 85.1667 |
| without_path_conflict | 84.5000 | 84.7333 | 84.7250 |

Waiting을 제거하면 세 탐색 방법에서 모두 평균 완료시간이 늘었다. 무작위와 BO의 nominal 시나리오 bootstrap 구간은 0을 포함하지 않았지만, PSO의 구간은 0을 포함한다. 나머지 세 변수는 제거 시 평균이 좋아지는 방법도 있어 네 변수가 모두 필수라는 결론을 지지하지 않는다. BO의 exit 제거, PSO의 path 제거는 full보다 평균이 낮고 nominal 구간도 0 아래지만, 작은 개발 자료에서 반복 비교한 탐색 분석이다. 전역 최적해 간 비교, 다중 비교를 보정한 확증 결과, 독립 최종 테스트가 아니다.
